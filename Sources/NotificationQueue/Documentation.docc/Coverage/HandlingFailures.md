# Handling Failures

Respond to scheduling results, preserve retryable work, and surface errors.

## Returned Results

Every successful coordinator operation returns a ``NotificationQueue/ReminderJournal`` with a populated ``NotificationQueue/ReminderJournal/lastOutcome``. It lists ordinary reminders verified as pending, future reminders deferred in storage, and saved reminders whose dates elapsed. Elapsed dates do not prove delivery. The outcome also explains the warning status and indicates when the app must generate a new schedule window.

`lastOutcome` is optional because a new or older journal may have no completed pass. A stored outcome describes its last successful pass; it is not current evidence after a failed operation.

## Per-Reminder Diagnostics

``NotificationQueue/ReminderJournal/reminderDiagnostics`` retains the latest evidence for each reminder ID. Read it from a returned journal or call `try notifications.diagnostics()` after a failed operation. This read throws storage errors and does not itself refresh or infer delivery.

| State / reason | Meaning |
| --- | --- |
| Deferred / capacity | The pending budget or other system requests left this reminder in overflow. This is not yet a missed reminder. |
| Awaiting scheduling / submission failed | The notification store threw while adding the request. `detail` retains its error text. |
| Awaiting scheduling / scheduling unconfirmed | Submission may have happened, but verification did not complete. |
| Elapsed / no verified refill before deadline | An occurrence last known to be deferred expired before a refill verified it as scheduled. |
| Elapsed / submission failed | A rejected submission remained unresolved at the deadline. |
| Elapsed / scheduling unconfirmed | There is insufficient evidence to establish scheduling before the deadline. |
| Elapsed / delivery unknown | The occurrence was previously verified as pending; this does not prove it was presented. |

Call `refresh()` when execution resumes to detect elapsed occurrences. Elapsed evidence survives subsequent refreshes and app restarts. Rescheduling the same ID starts a new occurrence and replaces that ID's prior diagnostic; this is a latest-occurrence report, not an unlimited event history. Records for cancelled future reminders are removed. Older journals without diagnostics remain readable; their elapsed occurrences are reported as unconfirmed.

A missing verified refill does not identify its cause. The host might not have called the coordinator, iOS might not have granted time, or an attempted refill might have failed. Background task submission alone proves none of these. Operation-level permission, storage, verification, and cancellation errors still throw and reach `onEvent`; they must not be presented as proof that every reminder in a batch failed.

Finite generated schedules also report `lastOutcome.generationBoundaryReached`. The host must generate another window; no per-reminder error can identify events that have never been supplied to the queue.

## Errors and Observation

Use `do` / `catch` at the operation's call site. Invalid policies, duplicate or reserved IDs, expired new input, unavailable capacity, authorization failures, persistence failures, submission failures, and pending-request mismatches are reported rather than treated as success. Store reads and removals can throw too. Cancellation propagates as an error.

An optional observer can centralize logging or update app status:

```swift
notifications.onEvent = { event in
    switch event {
    case .completed(let journal):
        // Inspect journal.lastOutcome to update your app's scheduling status.
        print("Deferred reminders:", journal.lastOutcome?.deferredReminderIDs ?? [])
    case .failed(let error):
        // Route this to your app's error reporting or visible status.
        print("Notification scheduling failed:", error.localizedDescription)
    }
}
```

The observer runs on the main actor. It does not replace catching thrown errors, and a failure is observed once per operation. Capture the coordinator weakly if the closure refers to it. There is no implicit retry loop; your app decides when another execution opportunity is available.

## Recovery

Validation rejects an invalid update before saving it. Once new intent has been saved, a scheduling failure leaves the journal marked for reconciliation. Call `refresh()` after resolving the problem. If persistence failed, resubmit the desired batches because their new contents may not have reached disk. A corrupt journal throws instead of silently resetting to an empty queue.

Already elapsed saved reminders are pruned and reported. Newly submitted elapsed reminders are rejected so the app can correct their dates. Finite source windows must be regenerated by the host when their boundary is reached; replaying the journal cannot invent new events.

## Verification Boundaries

The Apple adapter checks authorization and reads pending requests back to verify identifiers and contents, including removals. Missing, unexpected, or changed requests produce an error. Custom stores must honestly implement their throwing operations and authorization checks; the default authorization hook is a no-op for stores that have no permission model.

Successful verification is a snapshot, not a delivery receipt. Apple does not expose an error for every later presentation decision or promise background execution. Focus, individual alert settings, later permission changes, and system behaviour may prevent visible presentation. No callback runs while the app has no execution time. Coverage warnings themselves use the same notification system.
